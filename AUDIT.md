# Security and reliability audit

This review started from a clean fresh clone of `main` at commit `1c5d31727744e8844fa48285d5169483f49be435` (2026-10-03, after PR #12). Before edits, the latest Pages deployment pointed at that SHA; the HTTPS site returned 200 and `python3 scripts/verify_pages.py --timeout-seconds 60 --interval-seconds 5` confirmed byte-identical application and snapshot assets (15,318 records, 31 shards). The security-check and Pages workflows had passed for that SHA. `main` remained unprotected with no ruleset. No data-source refresh was run during this review.

## 2026-10-03 re-audit and swipe navigation

The quick re-audit found no new actionable security or reliability defect in safe text rendering, URL validation, snapshot schema and SHA-256 checks, duplicate and size limits, malformed-data handling, CVSS/EPSS validation, CSP, fail-closed updater behavior, atomic publication, or GitHub Actions permissions. The captured EPSS scores are dated 2026-09-29 and correctly marked stale; no security control or snapshot data was changed.

The new touch-only navigation uses native Pointer Events and the existing `switchPage` state source. A horizontal drag follows the finger and settles back or changes only to an adjacent page; edge swipes do not wrap. Vertical scrolling and pinch zoom remain enabled. Buttons, links, form controls, CVE/feed interactions and selection gestures do not trigger navigation; text selection is allowed and cancels an in-progress swipe. Community's safe terminal panel remains swipeable, while its controls and links remain excluded. The existing tabs, URL/history handling, CVE details and ARIA state remain in place. Reduced-motion mode skips the slide and still allows navigation. No dependency or infrastructure was added.

Browser testing exposed and fixed two interaction defects: Chromium can report pointer-capture loss before its normal `pointerup`, so release and cancellation now resolve at document scope; and a new gesture now cleanly stops an in-progress spring-back instead of being ignored. One test's lower-right start correctly hit a CVE button and was blocked; the test now uses a verified safe page margin rather than weakening that exclusion.

## Client-side findings and fixes

The previous client loaded every manifest-listed file without authenticating its bytes or placing an upper bound on the transfer, parsed size or number of records. The new loader validates the manifest and all sidecars against explicit schemas and verifies SHA-256 digests before accepting each resource. It limits the manifest to 512 KiB, the Overview sidecar to 64 KiB, each shard to 16 MiB, EPSS to 4 MiB and the complete static JSON snapshot to 128 MiB; it also caps the feed at 50,000 records and 31 days, sets a 12-second request timeout, and loads at most six day shards concurrently. A shared manifest promise avoids duplicate requests when Overview and CVE Center are opened close together.

The browser now rejects unsafe shard paths, duplicate dates or CVE identifiers, malformed dates and timestamps, inconsistent counts, unsupported source/severity values, malformed score data and mismatched digests. Missing or corrupt data yields a clear generic failure state rather than an empty-looking healthy dashboard or an exception detail. Overview counts, latest records and timestamp are hydrated from validated feed data instead of stale HTML examples. The main UI continues to keep CVSS, EPSS and KEV evidence separate; no arbitrary combined priority heuristic was introduced.

Titles, descriptions, reference labels and other feed-controlled strings are rendered as text nodes, not HTML. Parsed HTTP(S) links reject credentials and active schemes and open with `noopener noreferrer`. The regression suite injects hostile title/description/reference payloads and confirms they remain inert and cannot create elements or execute script. The page contains no inline JavaScript or `innerHTML`/`eval` rendering path.

`index.html` now has a restrictive same-origin meta CSP: same-origin scripts/styles/data connections, no objects, no base URL and same-origin form actions. The design's pointer parallax writes bounded numeric CSS variables, so the policy allows inline style attributes; inline scripts remain disallowed. The HTML also sets a strict-origin referrer policy. A Pages meta policy cannot enforce `frame-ancestors`, and this repository's branch-based GitHub Pages configuration does not expose a custom HTTP-header setting; clickjacking headers therefore remain a hosting-level limitation.

## Ingestion, data integrity and publication

The former updater and Actions workflows were recovered from Git history and audited rather than copied as-is. Their data layout no longer matched this redesign, the old capture helper targeted an endpoint that currently returns 404, and the former writer replaced output files individually. The obsolete `capture_snapshot.py` helper was removed. The restored updater writes the current `snapshot/manifest.json` plus `snapshot/data/` layout and stages a complete snapshot in a sibling directory. It runs the same offline validator before replacing the previous directory and rolls back if the directory swap fails.

Upstream requests are restricted to the official HTTPS source hosts and same-host HTTPS redirects. JSON parsing rejects duplicate keys and non-finite JSON constants; response bodies are individually bounded at 32 MiB and combined JSON ingress is capped at 256 MiB. NVD pagination must be complete with consistent totals and identifiers; GitHub advisory pagination rejects off-origin or repeated cursors; CISA metadata count must match a non-empty, unique catalog. EPSS compressed and expanded sizes, rows, lines, duplicate identifiers and score ranges are bounded. Any empty, malformed or incomplete NVD, GitHub or CISA core source fails closed before publication. A bad optional EPSS update may retain the prior score map only when the manifest accurately marks it stale or unavailable.

The strict offline verifier rejects unsafe paths, symlink roots, duplicate JSON keys, unexpected files, inconsistent schemas/counts/totals, invalid URLs, malformed EPSS values and hash mismatches. The one-time legacy migration that added current-layout metadata was tested to preserve every existing daily-shard and EPSS byte and the original snapshot timestamp. In this branch, no existing day shard or EPSS file differs from the captured baseline; the new Overview sidecar is derived from those same records.

The new `checks.yml` workflow uses read-only repository permissions for pull requests and main pushes, and disables persisted checkout credentials. The refresh workflow runs every six hours UTC or by manual dispatch from `main` and separates three jobs: a read-only `prepare` job performs source ingestion, package installation, tests and browser checks; a minimal `publish` job revalidates the artifact and alone receives `contents: write`; and a read-only `verify-pages` job checks the public deployment. Checkout credentials are never persisted, and the write-capable token is passed only to the single `git push` step. The source API token in `prepare` is read-only, and no stored NVD secret is required. All GitHub Actions are pinned to immutable commit SHAs verified against their upstream repositories. No package is added to the runtime site; the pinned Playwright toolchain is for tests only.

Before a data commit, the scheduled workflow runs fixture-based unit tests, snapshot validation with a 36-hour freshness gate, the full browser feed suite and the Community suite. The publisher checks that `main` still matches the exact validated base revision, independently validates the downloaded snapshot artifact, stages only `snapshot/`, and refuses to rebase or force-push if `main` moves. It does not invoke a Pages deployment bypass. The PR/check workflow never receives a write-capable credential.

The public Pages byte-for-byte check is necessarily **post-publish**, not a gate that can be passed before the commit: this repository's only Pages source is `main`, so an unmerged candidate is not served at the production URL. The post-publish job runs read-only and waits for the public site to serve byte-identical app HTML/scripts/styles, manifest, sidecars and all shards with their declared hashes. A failed or timed-out public check reports a failed workflow after the commit; it cannot prevent the already-authorized Pages deployment from starting. The same limitation applies to the initial application PR: branch-based Pages has no candidate preview URL. Do not describe that remote check as pre-merge verification of the unmerged candidate.

## Verification and remaining limits

Final local checks passed JavaScript syntax for `app.js` and `community.js`, Python compilation, offline validation of the full checked-in snapshot, and **35 unit tests** covering snapshot integrity, legacy migration, URL/path policy, source pagination, EPSS parsing, byte limits, rollback, previous-snapshot preservation and workflow permission boundaries. Snapshot validation confirmed **15,318 CVEs across 31 UTC shards**, 14,760 EPSS values, and 34,727,135 JSON bytes; EPSS remains marked stale-or-unavailable.

The final full-feed Chromium suite passed across all **15,318 records** and **31 shards**, including manifest-driven totals, severity/date/search filters, pagination, detail and focus restoration, Overview hydration, hash-tamper rejection, oversized-response rejection and inert hostile text. Its new mobile touch tests passed finger tracking, adjacent routing/no wrap, control exclusion, safe Community terminal gestures, selection cancellation, vertical/diagonal scrolling, detail/search/pagination preservation, URL/history, reduced motion, keyboard/ARIA state and desktop mouse non-interference. Overview, CVE Center and Community had no horizontal overflow at 320, 360, 390, 412, 768, 1024 and 1440 CSS pixels; the run ended with no browser/page/console errors, failed requests or automatic external requests.

The standalone Community browser suite passed at ten viewport sizes. It exercised native keyboard activation, visible focus, reduced-motion behavior, accessible live status, duplicate-action protection, cancellation on page change, browser-history return and the exact Telegram destinations. All nine Overview/Center/Community screenshot comparisons were pixel-identical to `origin/main`; every Telegram request was fulfilled by a local Playwright route, with zero browser errors and no contact with Telegram. The existing image-diff test emitted a non-fatal Pillow deprecation warning for `Image.getdata()`.

This audit's snapshot remains the dated **2026-10-02T06:00:04Z** capture, with **14,760** EPSS values dated **2026-09-29** and marked stale. The updater was tested only against deterministic fixtures and was not run against live sources. The public byte-for-byte Pages check passed against the pre-edit `main` baseline; this feature branch was not pushed or deployed and therefore has no candidate Pages URL. SHA-256 here provides consistency against the received manifest, not a signature or independent source authenticity.

The repository currently has no main-branch protection or rulesets. Future data-only refreshes make a direct `main` commit after the read-only fixture, snapshot and browser gates; no repository rule requires a human review. This preserves automatic freshness but is a deliberate trade-off; requiring human review would mean changing the updater to a PR-based flow. The Pages byte-for-byte check runs after that commit and cannot prevent its deployment from starting. GitHub Pages also cannot set the missing response headers from this repository configuration. The application remains static: upstream outages, source limits and scheduled-run failures can delay freshness; no server-side filtering, live alerts, formal screen-reader audit or physical-device validation is part of this implementation.
