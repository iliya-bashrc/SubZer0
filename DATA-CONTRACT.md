# Snapshot and history data contract

This document describes the static files read by the browser and generated by `scripts/update_data.py`. `snapshot/manifest.json` and each declared SHA-256 digest are authoritative for a particular capture; recorded source statuses are not live health checks.

## Capture times and provenance

The manifest describes a complete rolling 30-day UTC activity capture. Full CVE records retain the source publication date and source modification/update timestamps. `activity_at`, `date_basis` and `window_date` identify the newest eligible activity used to place a record in a day shard. A recently modified CVE does not receive a new publication date.

The product keeps three clocks distinct:

- **Source time** is a date or timestamp supplied by NVD, GitHub, CISA or FIRST.
- **Observation time** (`history.events[].observed_at`) is when a complete updater run compared the current result with its previous complete capture.
- **Capture time** (`manifest.generated_at`) identifies the validated snapshot currently being served.

Source-check statuses are a record of the run that generated the snapshot. They are not telemetry or a live source probe.

## Manifest and sidecars

`manifest.json` uses schema version 2. It declares paths, schemas, sizes, SHA-256 digests and counts for each sidecar and UTC-day record shard. The producer stages the entire candidate, runs the offline validator, and replaces the prior capture atomically. A core-source or validation failure leaves the prior snapshot intact.

| File | Purpose | Schema and limit |
|---|---|---|
| `data/overview.json` | Up to 50 source-activity-ordered records for Overview and Latest, plus a bounded observed-change preview | Schema v3; 64 KiB |
| `data/search-index.json.gz` | Compact column-packed list/search fields for every CVE record | Schema v3; 3 MiB compressed and 12 MiB uncompressed |
| `data/epss.json` | FIRST score, percentile, score-set date and capture status | Schema v1; 4 MiB |
| `data/history.json` | Complete-capture metadata and bounded source-backed changes | Schema v1; 8 MiB, 10,000 events and 800 capture entries |
| `data/YYYY-MM-DD.json` | Full source records for one UTC activity day | Up to 31 shards, 16 MiB each |
| All snapshot JSON | Logical uncompressed JSON bytes used for the snapshot-wide bound | 128 MiB total |

The manifest is limited to 512 KiB, the feed to 50,000 records, a fetch to 12 seconds, and concurrent detail-shard loads to six. The gzip index is counted by its expanded JSON size toward the total logical-data limit.

## Compact search index

The v3 index is a deterministic gzip artifact. The manifest records both the compressed `bytes`/`sha256` and the uncompressed `uncompressed_bytes`/`uncompressed_sha256`. The browser and offline validator bound the compressed and expanded streams and verify both digests before parsing JSON. An index row is an 11-column array:

1. CVE ID
2. Title
3. Normalized description summary (up to 320 characters)
4. CVSS score or `null`
5. Severity code: `critical`, `high`, `medium`, `low`, `none`, `unknown`
6. Whether CISA KEV membership is present
7. Source-derived activity timestamp
8. Activity-basis code: CVE publication, GitHub advisory publication, NVD last modified, GitHub advisory updated, or CISA KEV date added
9. Source bitmask: NVD `1`, GitHub Advisory Database `2`, CISA KEV `4`
10. Up to eight bounded vendor/product/version-hint triples; version hints are retained only for the first three products and capped at 160 characters
11. Up to eight validated GitHub advisory IDs

EPSS values and KEV evidence remain in their own validated sidecars/full records; they are not blended into CVSS. The compact index intentionally omits full descriptions, references, exact CPE configurations, detailed version ranges, CVSS vectors and per-source evidence. Those fields remain in the full-record day shard. Where the source supplies CVSS version, vector and scoring source, the updater preserves them in that record; it does not invent missing evidence. NVD's CVSS 2.0 `vectorString` is retained in its source-native, unprefixed form; version 3.0/3.1/4.0 vectors retain their prefixes. Source, offline and browser validators enforce version-specific syntax and a 512-character vector bound without truncation. Search results are limited to fields actually indexed, and a miss in an unindexed reference or long description is not proof that the dossier lacks it.

The offline validator ties each compact row back to its full record, checks its derived source/severity/activity fields and confirms that its detail path resolves to the right UTC shard. The client repeats size, digest, schema and detail-consistency checks before use.

## Change-history sidecar

`history.json` records observations made by comparing complete captures. It contains:

- `baseline`: prior complete-capture metadata when known; legacy captures are not assigned invented observation timestamps;
- `snapshots`: complete-capture entries retained for up to 30 days and capped at 800;
- `events`: material differences retained for 30 days and capped at 10,000;
- `kev_catalog`: bounded complete CISA catalog state when available, capped at 5,000 entries and 4 MiB.

An event includes its CVE ID, change type, `observed_at`, source-provided `source_time` (or `null` when absent), source attribution, and bounded before/after values. Event families cover new or re-observed CVEs, CVSS and record metadata, affected products/version ranges, advisory/reference changes, material EPSS changes, CISA KEV additions/changes/removals, and a grouped `CVE_UPDATED` marker.

A new-CVE event requires a source publication time later than the prior complete capture. If a CVE re-enters the rolling feed after an out-of-window modification, it can be labeled `CVE_REOBSERVED`; the UI explains when the old field-level record is unavailable. Omission from a rolling feed is never treated as deletion. Older KEV entries are compared against the separately retained full catalog. CISA supplies an entry date, not a modification timestamp, so KEV changes can have `source_time: null` while retaining their actual SubZer0 observation time.

EPSS membership additions/removals retain the score-set timestamp when supplied. To reduce noise, score-to-score changes are emitted for an absolute move of at least 0.01 or a twofold move when the higher score is at least 0.05; the complete sidecar still carries the raw values. Overview's preview contains only a bounded set of the newest eligible events for current CVEs. The offline validator requires each preview item to match the corresponding retained history event and current record title.

A migrated capture without an earlier comparable full snapshot is an explicit baseline and may truthfully contain no events. This checked-in snapshot instead carries events derived by the normal producer from successive complete captures whose manifest times are retained in `history.json`. The browser tests use isolated synthetic responses for uncommon event types without writing test-only events into production history.

## Offline integrity and trust

The service worker stores same-origin app assets and bounded snapshot artifacts in versioned offline cache `subzero-offline-v4`. It caches the compressed index bytes; the application still verifies the compressed and expanded hashes and schema before display. A fresh manifest is checked online before cached artifacts are treated as candidates. Offline fallback reports the verified capture age and refuses to display an uncached or invalid dossier shard.

SHA-256 checks consistency against the same-origin manifest. It is not a digital signature and cannot prove authenticity if both a file and its manifest are replaced together. Snapshot text is untrusted: the application renders it as text, validates reference URLs, and opens external destinations with `noopener noreferrer`.

## Local validation

```bash
python3 scripts/verify_data_snapshot.py
python3 -m unittest discover -s tests -v
python3 verify_full_feed.py
```

Unit tests use deterministic fixtures. The browser suite exercises the checked-in capture and explicitly intercepted test responses; it does not refresh upstream sources.
